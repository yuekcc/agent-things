应用 Jeff Patton 的 user story mapping 方法论分析需求，拆分 user stories。沿设计路径推进，在关键检查点确认：活动骨架、发布切片、PRD 草稿。若用户要求纯技术设计，说明本 skill 不适用，并建议技术设计模板。

## 设计路径

1. 生成活动骨架。确定用户与范围，按时间顺序串出 3–7 个用户活动（backbone）。
2. 分解任务并写故事卡草稿。每个活动下列用户任务/故事卡，动词开头，面向目标。
3. 排优先级。先按价值/风险分桶，再按依赖/成本调整；可用 MoSCoW/WSJF 等。此步不是切片。
4. 纵向切片。每个发布切片跨多个活动，端到端、可交付、可验证、有价值；切片 1 优先覆盖核心活动的最小端到端路径（walking skeleton/MVP）。
5. 细化用户故事。As a <role>, I want <capability/action>, so that <benefit>。
6. 写验收标准。Given <前提>, When <动作>, Then <结果>。每条可测试，覆盖正常流、异常流、边界、权限、非功能（如适用）。
7. 自检。故事符合 INVEST（尽量独立，允许切片内依赖，切片间依赖显式记录）；AC 可测；切片可独立交付；目标可度量；关键歧义已确认或标记；可追溯：目标→活动→故事→AC→指标。
8. 输出 PRD。默认当前目录 `PRD.md`，或用户指定；若文件已存在，先询问覆盖、追加或另存。语言跟随用户，模板可翻译但字段结构不变。

## 提问原则

只问决策和意图：目标、范围、优先级、成功指标、用户偏好、取舍。每轮最多 3 问。先写当前理解与假设，再问阻塞问题。总轮次 ≤ 5。若目标/用户/范围缺失，先追问；轮次用尽仍未确认则记假设和开放问题，继续输出，不无限追问，并标注“假设版，不可评审，仅用于澄清”。

事实自己查，查不到再问。可查事实：文件、代码、配置、日志、公开资料、竞品。如环境支持子代理则派子代理查，要求返回结论、证据、置信度、未找到；主代理复核。不能派就自己查。不主动读取/输出密钥、凭证、个人敏感数据；如任务必须，先说明用途并获明确授权，且脱敏处理。

      - 依赖：
